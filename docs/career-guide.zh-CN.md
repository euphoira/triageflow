# 把项目变成能讲清楚的求职作品

适用方向：AI 应用开发、Agent 工程、Python 后端与大模型应用。

## 简历表述模板

下面的表述对应项目现有实现。请先实际运行、阅读代码并完成自己的改动，再根据真实参与情况使用。
不要把生成项目等同于已经具备全部实现经验，也不要填写不存在的用户量或线上收益。

**TriageFlow｜基于证据链的代码故障分析 Agent｜Python / FastAPI / SQLite / Tool Calling**

- 构建 Planner–Investigator–Reviewer 多角色工作流，通过受限仓库工具检索代码，生成包含
  文件路径、行号、原文引用与验证计划的故障分析报告，并提供可视化执行看板。
- 实现有界工具调用、结构化输出校验、独立上下文审阅与确定性引用核验；对证据不足返回
  低置信度结果，避免将未经检查的源码引用直接作为分析依据。
- 基于 SQLite 设计检查点和事件日志，支持中断恢复与历史回放；模型调用前持久化预算，
  保证恢复不会重置调用次数，并覆盖异常、取消与半轮工具调用中断场景。
- 建立工具/模型协议/工作流/API 回归测试与跨平台 CI 配置，提供无需密钥的离线演示及
  8 个合成评测用例，明确区分工程回归指标与真实模型质量。

测试数量以你发布版本的 `pytest` 输出为准；CI 在 GitHub 真正运行后才能写“跨平台 CI 通过”。
只有在真实评测后，才能加入“定位准确率”“平均耗时”“成本降低”等数字，并附数据集、基线和环境。

## 两分钟项目介绍

“我想解决模型排查 Bug 时结论看似合理、但缺少证据和可追溯过程的问题。
TriageFlow 先让规划角色拆解问题，再让调查角色通过函数调用检索源代码，最后让独立审阅角色
检查结论。系统层面不直接相信模型给的引用，而是核对文件、行号和原文，并检查是否真的读过。

我重点关注的是运行可靠性：工具范围受限，循环有预算，失败会留检查点，重启可以继续。
其中比较容易忽略的问题是，一轮模型回复可能包含多个工具调用，如果中途崩溃，不能保存成
不完整的对话协议；所以我只在整组工具结果完成后保存对话，同时提前记录预算。

目前它是本地单用户工具，提供离线样例和真实模型接入。离线评测用于回归，不代表模型准确率。
后续我会加入真实 Issue 数据集，比较单 Agent 与独立审阅的定位质量、耗时和成本。”

把其中的“我”改成与你真实承担的工作一致的描述。

## 面试深挖与回答要点

| 问题 | 回答重点 |
| --- | --- |
| 为什么是 Agent，而不是几次固定 Prompt？ | Live 的调查阶段由模型选择工具和参数，根据反馈继续检索；外层工作流受控。Demo 本身是规则演示。 |
| 多 Agent 一定更好吗？ | 不能假设。独立审阅可能减少漏检，也增加耗时与相关性偏差；需要与单角色基线做对照实验。 |
| 为什么没用 LangGraph？ | 当前图小、分支少，显式状态机更易展示持久化边界；复杂审批与分支增多时再评估框架。 |
| 怎样防止模型编造引用？ | schema + 文件/行号/原文核验 + 本次读取溯源。引用正确仍不等于语义正确。 |
| Prompt injection 怎么处理？ | 仓库内容是数据；更关键的是工具只读且无 shell/network/write，缩小可产生的影响。 |
| 如何恢复？ | 角色检查点跳过已完成阶段；不完整的只读工具轮可能重做，预算保留。不是 exactly-once 计费。 |
| 为什么不用向量库？ | Bug 线索常为标识符与错误文本，词法检索先建立基线；大型仓库再测量符号/向量检索收益。 |
| SQLite 能扩展吗？ | 当前是本地单进程设计；多进程需租约、队列、认证、状态迁移与调度隔离。 |
| 评测 8/8 意味着什么？ | 只说明合成固定场景的回归通过，不能外推真实根因诊断准确率。 |

## 建议亲自完成的四次迭代

1. **跑通并复述**：启动三个示例，查看每条引用，阅读 engine/store，故意触发预算不足并恢复。
2. **增加第四个故障**：自行设计文件、英文/中文描述、回归测试；提交可解释的 Git commit。
3. **真实模型对照**：使用自己的公开小仓库整理 20–30 个带标签的问题，记录模型、基线、
   文件命中率、引用有效率、拒答率、耗时和 token；保留失败案例，避免只挑成功示例。
4. **做一个深入改进**：例如符号检索、Responses 适配、独立审阅消融实验或多进程租约。
   用数据说明该改进的收益及代价，而不是只增加框架数量。

## 五分钟演示顺序

1. 展示定位到代码的免费订单报告，点开原文证据。
2. 查看 Planner → Investigator → Reviewer 与工具输入/输出日志。
3. 切换到无关问题，展示证据不足和低置信度。
4. 展示恢复测试与预算保留的实现，而不是只讲设计名词。
5. 打开评测输出，说明目前的边界和下一轮真实评测计划。
